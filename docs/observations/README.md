## Evidence threshold

Before recommending deeper runtime work, collect at least two successful live runs across separate local sessions after local Codex authentication has been established.

Use the following decision labels:

- `go`: at least two successful runs across separate local sessions, no blocking reactive auth/quota/rate-limit/backend-shape failures, source comparison reviewed, and billing-attribution limitations documented.
- `conditional_go`: separate-session success exists, but source comparison remains source-limited or billing attribution remains ambiguous.
- `needs_more_evidence`: live results are missing, contradictory, or too sparse to support a recommendation.
- `no_go`: authentication, backend-shape, quota/rate-limit, transport, billing-attribution contradiction, or safety failures block the direct backend path.

## Safe observation shape

Each observation should distinguish observed facts from interpretation. Record:

- date and local time with timezone
- observer initials or handle, if useful
- local Codex CLI version when known
- command path or validation path used
- whether the run was transport, runtime, usage/quota, or CLI validation
- normalized result status
- redacted request-shape notes
- redacted response/error-shape notes
- reactive usage/quota signals when exposed by status codes, headers, or error messages
- human billing-attribution notes that avoid account details and acknowledge ambiguity
- follow-up interpretation or recommendation

## Redaction rules

Never include:

- tokens, refresh tokens, ID tokens, cookies, or auth headers
- raw `~/.codex/auth.json` contents
- raw backend request or response payloads
- raw script contents
- private account identifiers
- private absolute paths by default
- unredacted personal data
- production credentials or private endpoints

Prefer bounded, low-cardinality observations such as normalized statuses, HTTP status classes, safe counts, redacted field names, and high-level shape notes.

## Repeated-session manual validation procedure

This procedure is for intentional human validation only. It is not part of the
default test suite or CI, and it must be run only after deciding to collect live
viability evidence.

1. Authenticate locally when needed:

   ```bash
   codex login
   ```

2. Start a local session and assign it a safe label, such as `session-1`. A
   separate session means a fresh terminal or later local validation session
   after authentication state has already been established; do not record private
   terminal paths, usernames, account IDs, or shell history.

3. In that session, run explicit live validation commands and record each result
   as a separate observation row or note:

   ```bash
   make test-live-codex
   make test-live-runtime
   make run-live-cli PROMPT="Reply with the single word: pong"
   ```

   Treat `make test-live-codex` as transport evidence, `make test-live-runtime`
   as runtime evidence, and `make run-live-cli` as optional CLI evidence.

4. Optionally run the marker directly when investigating the transport path:

   ```bash
   FABRICA_RUN_LIVE_CODEX_TESTS=1 uv run pytest -m live_codex
   ```

5. Record usage/quota evidence as a separate `usage_quota` observation only when
   a reactive signal is available, such as a response status, safe rate-limit
   header, normalized error category, or bounded error message summary. Do not
   expect exact per-session, per-call, or billing-attribution telemetry for the
   subscription-backed path. Do not copy account identifiers, billing pages, raw
   JSON, tokens, cookies, private URLs, or screenshots with personal data.

6. Repeat the live validation in at least one separate local session, labeled
   safely as `session-2` or similar. Do not recommend `go` or `conditional_go`
   until at least two successful runs across separate local sessions have been
   recorded. More sessions are useful when results are flaky, contradictory, or
   close to quota/rate limits.

7. Record only redacted observations in a dated note that follows the safe
   observation shape above. Keep observed facts separate from interpretation and
   record the separate-session success count after each observation.

8. Record failures with the same schema. Use these normalized failure categories
   when possible:

   - `auth_failure`: local authentication is missing, expired, rejected, or cannot
     be read through the explicit live path.
   - `rate_limit_or_quota`: the backend reports rate limiting, quota exhaustion,
     or usage access limitations.
   - `backend_shape_mismatch`: required headers, payload shape, streaming
     behavior, response fields, or error shape no longer match the adapter's
     expected private backend contract.
   - `transport_error`: network, TLS, timeout, DNS, connection, or unexpected HTTP
     transport behavior prevents a normalized backend result.
   - `other`: a failure that does not fit the categories above; include only a
     bounded, redacted summary.

Absence of public API billing evidence is not a permanent billing guarantee.
Billing attribution is expected to remain ambiguous unless a safe external
account observation is available. Treat quota evidence as reactive: successful
responses, quota/rate-limit errors, safe headers, and normalized error
categories.

Default `uv run pytest`, `make test`, imports, and CLI help must remain offline and credential-independent.

## Upstream Cline comparison notes: 2026-08-01

For a comparable subscription/client behavior reference, a shallow checkout of
`https://github.com/cline/cline` at commit `e543c69` was inspected locally. The
upstream Cline code classifies quota, rate-limit, subscription, and entitlement
states from returned status codes, error codes, and error messages rather than
from generic per-call subscription billing telemetry:

- `apps/vscode/src/services/error/ClineError.ts` classifies `429`, rate-limit,
  quota, `INFERENCE_CAP_ERROR`, `SPEND_LIMIT_EXCEEDED`, entitlement, ClinePass
  limit, and free-model limit messages into user-facing error categories.
- `sdk/packages/llms/src/providers/errors.ts` recognizes ClinePass subscription,
  ClinePass limit, and free-model limit messages such as "free limit reached on
  model" and reset-time text.
- `apps/vscode/src/services/account/ClineAccountService.ts` has Cline-account
  balance, usage transaction, and payment transaction endpoints, but those are a
  product account surface and should not be treated as proof that a private
  subscription-backed Codex path exposes exact per-session or per-call billing
  attribution.

This supports using reactive error/status evidence for this project: record
successful repeated runs and classify returned auth, quota/rate-limit,
entitlement, backend-shape, and transport failures when they occur. Do not block
viability on unavailable exact billing telemetry.
